# INTEGRATION-LEVELS.md — The UCH Integration Ladder

- **Status:** Approved design ([ADR-005](ADR-005-universal-cognitive-protocol.md))
- **Date:** 2026-07-31 (driver terminology per ADR-005 Amendment A, 2026-08-01)
- **Scope:** The capability ladder every driver (Universal Cognitive Harness) uses to
  participate at the level its host actually exposes — with graceful degradation,
  never privileged assumption.
- **Companions:** [EXOSYMBIOSIS.md](EXOSYMBIOSIS.md) (capture rails),
  [UNIVERSAL-INTEGRATION.md](UNIVERSAL-INTEGRATION.md) (hive architecture + roadmap),
  [LIVE-COGNITIVE-STATE.md](LIVE-COGNITIVE-STATE.md) (the L3 artifact)

## 1. Purpose

Not every platform exposes the same internals. Claude Code, Copilot, Codex, Cursor, and
OpenCode each have different extension surfaces and permissions (verified 2026-07-31
against official docs in EXOSYMBIOSIS §4/§6 and UNIVERSAL-INTEGRATION §2). A universal
driver (harness) must **participate at the level the platform actually exposes** and
gracefully degrade rather than assume privileged access everywhere.

## 2. Two axes — do not confuse them

| Axis | Ladder | Answer | Defined in |
|---|---|---|---|
| **Transport tiers** | T0–T4 | *How* UCH is reached (daemon/CLI/HTTP → MCP → ACP → A2A → native SDK) | `research/interfaces/universal-cognitive-harness.md` (Compatibility ladder) |
| **Integration levels** | L0–L4 | *What cognition* a host can reach (workspace events → session → tooling → cognition → native) | This document |

The axes are orthogonal. A host can reach UCH via MCP (T1) while contributing cognition
traces (L3). An adapter's level claim is always per-rail, and the transport tier never
implies a capability level.

## 3. The levels

| Level | Capability | What the driver contributes (observe) | What UCH returns (augment) | Examples |
|---|---|---|---|---|
| **L0 – Workspace** | Filesystem, Git, diagnostics, build/test events | Passive tails, git events, workspace.state events | Workspace graphs, DNA, health, event ledger | Available almost everywhere |
| **L1 – Session** | Session lifecycle, prompts, explicit plans, checkpoints, accepted edits | session.lifecycle, prompt.submitted, compaction capture | Context injection at session start, handoff, resume | Supported by several IDE agents |
| **L2 – Tooling** | MCP tools, terminal commands, external integrations | tool.call / tool.result, permission events, background.process | Capability registry, tool evidence, policy stance | Growing ecosystem via MCP |
| **L3 – Cognition** | Structured cognitive traces — goals, decisions, evidence, verification, lessons | Cognitive traces, live cognitive state reads/writes, traceparent propagation | Trace ledger + replay, Live Cognitive State, organic score | Provider-agnostic, created by UCH itself |
| **L4 – Native** | Deep platform-specific integration: extensions, plugins, hooks, agent SDKs | Full rail set (hooks + storage + protocol + OTel where present) | Full sync planes (genome/memory/skills/workspace/policy/cognition) | Depends on each vendor |

## 4. Rules

1. **Cumulative, but per-rail.** Levels are cumulative within a rail; they are
   independent across rails. A platform may be L4 on the hooks rail and L0 on the COT
   rail simultaneously. Every claim is `(rail, level)`.
2. **Never assume a level.** The substrate serves the highest *declared* level per
   capability. Declarations live in the driver manifest's **`level_claims`** field
   (extending the driver manifest contract of CIC §5 and
   `research/interfaces/universal-cognitive-harness.md` §Driver model), are visible
   to the user, and never silently escalate. A driver is served at the highest
   *verified* level, never the claimed one (COGNITIVE-PACKAGES.md §4 rule 3):

   ```jsonc
   // driver manifest — uch.package.v1 (COGNITIVE-PACKAGES.md §3)
   "level_claims": { "hooks": 4, "cot": 3, "otel": 0, "storage": 3 }
   ```
3. **L3 belongs to UCH.** L3 does not depend on the host exposing anything beyond L0–L2
   signals: the cognitive trace is *generated by the driver* from observable artifacts
   (plans, tool calls, actions, intermediate outputs, verification, summaries) — never
   from hidden chain-of-thought.
4. **Degradation is a feature.** If a rail breaks (platform update, permission change),
   the driver drops to its highest remaining level and declares it. Capture never dies
   — it degrades.

## 5. Conformance criteria per level

A driver may claim level Ln on a rail only when all criteria for Ln on that rail pass:

| Level | Criteria (all must hold) |
|---|---|
| **L0** | Receives or tails ≥ 1 workspace event stream (fs/git/diagnostics/build/test); emits normalized `workspace.state` events with provenance (EVENT-GOVERNANCE gate) |
| **L1** | Emits `session.lifecycle` and `prompt.submitted` events with native session ids; accepts context injection on session start (genome/memory/workspace planes) |
| **L2** | Emits `tool.call`/`tool.result`/`permission.*`; consumes ≥ 1 UCH capability via MCP (or other transport) |
| **L3** | Propagates/accepts W3C `traceparent`; emits or reads cognitive traces mapped to the OTel ledger (ADR-002); can read the Live Cognitive State document |
| **L4** | Native integration (extension/plugin/hooks/SDK) with ≥ 2 independent rails and full sync planes in one direction |

## 6. Verified per-platform level map (2026-07-31)

Derived from EXOSYMBIOSIS §4/§6 and UNIVERSAL-INTEGRATION §2 (official docs). Per-rail,
best currently achievable; degrade as declared.

| Platform | Hooks/plugin | Storage tail | Protocol client | OTel | COT |
|---|---|---|---|---|---|
| VS Code + Copilot | L4 (extension host) | L1–L2 (chat journals) | L4 (Agent Host Protocol, evolving) | L2 (opt-in OTel) | L0 (token counts only) |
| Claude Code | L4 (HTTP hooks, allowlist) | L3 (transcripts + thinking) | L4 (Agent SDK) | L3 (`CLAUDE_CODE_ENABLE_TELEMETRY`) | L2 (plaintext thinking) |
| Codex | L2 (command hooks; HTTP/agent parsed but skipped) | L3 (rollouts + reasoning items; some encrypted) | L4 (app-server JSON-RPC) | L3 (OTLP exporter) | L2 (summary; full content opt-in) |
| OpenCode | L4 (plugin events) | L3 (part storage incl. reasoning) | L4 (server SSE/REST) | L0 | L3 (plaintext reasoning parts) |
| UCH in-process (plugin boot) | L4 | L4 | L4 | L3 (OtelBridge) | L3 (explicit summaries only) |

Re-verify each row when a platform ships a new extension model — the level table is a
snapshot, the conformance criteria are the contract.

## 7. Relationship to the roadmap

| Milestone (UNIVERSAL-INTEGRATION §8) | Levels achieved |
|---|---|
| M0 — Hive core (passive) | L0 for all four platforms |
| M1 — Live adapters | L1–L2 for Claude Code, Codex, OpenCode, VS Code (per map) |
| M2 — Traces + COT vault | L3 (traces, live state, replay) |
| M3 — Bidirectional hive | L4 (full sync planes, headless drive) |

Today: the UCH MCP server is L2; the OpenCode plugin is L1–L2. The goal of the M-series is
L4-per-rail where vendors allow it, and honest L0–L2 elsewhere.
